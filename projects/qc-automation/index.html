Problem Statement

Cars24 Australia runs a dealer marketplace — dealers submit listings via the Autogate API, and each vehicle needs to be validated, enriched, and published to the internal DMS (Dealer Management System) before buyers can see it.

The challenge: data quality is inconsistent. Dealers fill in 20+ fields per vehicle, but spellings differ ("Auto" vs "Automatic"), fields are left blank, images are missing, descriptions are generic or missing entirely, and dealer data sometimes conflicts with what the Glasses reference database says about the same vehicle.

Before this engine existed, quality checking was manual: a human reviewer would open each record, cross-reference it, flag issues, and send it back to dealers for correction. For a marketplace with thousands of active listings refreshing every 4 hours, this didn't scale.

What I Built

A full automated inventory QC pipeline that sits between the Autogate API and the DMS publish gate. It:

Ingests dealer inventory data every 4 hours via the Autogate API and stores it in DB1.

Cross-references that data against Glasses vehicle reference data (DB2) — field by field, side by side in DB3.

Runs a rules engine that checks each field for completeness, validity, conflicts, and threshold criteria — classifying each issue as hard/high/low risk.

Resolves conflicts automatically for low-risk fields (dealer wins); flags high-risk conflicts for review.

Calls Claude API for description generation/rewriting, fuzzy variant matching, image QC, and dealer comments safety.

Scores each listing 0–100 across 5 weighted dimensions.

Writes results to DB5 (master store) as GTG, Pending, or Hard Fail.

Syncs to a Google Sheet for the ops team — single-click approval to trigger DMS publish.

How It Works

01
Autogate API poll (every 4h)
Cron triggers main.py. The Autogate poller fetches the latest dealer inventory, writes raw records to DB1. Multiple DMS sources (Autogate, EasyCars) feed into the same schema.
02
Glasses reference merge
For each VIN, the engine looks up spec data from DB2 (Glasses API). Both dealer values and Glasses values are written side by side into DB3 — e.g., make_dealer vs make_glasses, transmission_dealer vs transmission_glasses — giving the QC engine a direct comparison for every field.
03
Re-queue logic
Before running full QC, the engine checks if the VIN already exists in DB5. If it's GTG, only material changes trigger a re-run. If it's Pending, only the previously-failed fields are re-checked. This avoids redundant processing on every 4-hour cycle.
04
Rules engine
qc/engine.py loops through 20+ field rules defined in config/field_rules.py. Each field has: mandatory level (True / publish / conditional / preferred), source priority (dealer first, Glasses fallback), risk classification (hard / high / low), normalisation map (body type enum, fuel type enum, colour synonyms, etc.), validation function (VIN format check, year range, price > 0, odometer plausibility), and on_blank / on_conflict behaviour.
05
Conflict resolution
qc/conflict_resolver.py handles cases where dealer and Glasses values differ. Low-risk fields: dealer wins, discrepancy logged. High-risk fields (transmission, engine capacity, year): flagged for human review. Hard fields (VIN format, price = 0): automatic failure.
06
Claude AI layer
Four selective AI tasks — not run on every record: description_generate: blank or low-quality descriptions → Claude writes a 150-word customer-facing description from vehicle specs. description_rewrite: present but poor descriptions → Claude rewrites preserving facts. fuzzy_field_match: variant/badge/series conflicts where values are similar → Claude resolves with confidence score. image_qc: Claude Vision checks first 3 images against listed make/model/year. comments_safety: dealer comments checked for false claims, prohibited content, pricing contradictions.
07
Scoring
qc/scorer.py assigns a 0–100 score across 5 weighted dimensions: identity completeness (30pts), vehicle basics (20pts), price/odometer validity (15pts), conflict severity (15pts), image threshold (10pts), description quality (10pts). Score bands: 90–100 = GTG auto-write, 75–89 = GTG minor gaps, 50–74 = Pending/exception queue, 0–49 = Hard Fail/hold.
08
Google Sheets sync + DMS publish
outputs/sheets_sync.py writes all Pending records (and recent GTG) to a Google Sheet. Ops team sees: VIN, stock number, make, model, QC status, score, failed fields, dealer vs Glasses values. A single "Ops Approved = TRUE" checkbox triggers the DB5 status update and queues the record for DMS publish.

Limitations & Future Improvements

Human approval gate (v1): currently GTG listings still require a single ops click before DMS publish. v2 plan: auto-publish for score ≥ 90 with no hard fails.
VIN-level image matching: current image QC checks make/model/year against the first 3 images; a more precise model would check every image and flag specific mismatches by type (exterior, interior, engine bay).
Dealer feedback loop: Pending records are visible in the Google Sheet but there's no automated notification back to the dealer. A future version would trigger a structured email/webhook to the dealer's DMS with the specific failed fields.
Full version history in DB5: v1 stores latest state only; v2 will add a complete change log for audit purposes.
