Vehicle Recall Checker

Live · Cars24 AU

A Flask REST API that looks up any VIN against a SQLite recall database — serving a Cars24-branded HTML frontend. Three endpoints: /lookup (VIN query), /status (database stats), /health. Deployed behind gunicorn, CORS-configured.

Problem Statement

Cars24 AU needed a way to check whether any vehicle in its inventory had an active recall notice — without depending on a paid external API call for every single lookup. The solution needed to be fast, deployable, and accessible via a simple browser frontend for the ops team.

What I Built

A Python Flask API with three endpoints backed by a local SQLite recall database:

GET
/lookup?vin=VIN
Returns all matching recall records for a given VIN. Strips whitespace, uppercases the input, queries the database, and returns structured JSON with found status, recall count, and an array of recall objects.
GET
/status
Returns total VIN count and number of distinct source files in the database. Useful for ops to verify the database is populated and up to date.
GET
/health
Simple liveness check — returns {"ok": true}. Used by the deployment platform for liveness probing.

A static HTML frontend (Cars24-branded, Geist font, blue/mint palette) calls the API and renders results in real time. The whole system is CORS-configured so the frontend can be hosted separately from the API.

How It Works

01
Database
vin_database.db is a SQLite database with a recalls table. Each row has: recall_id, source_file (which recall data file it came from), and raw_row (the original recall record). Indexed on vin for fast lookup.
02
API — /lookup
Accepts a VIN via query param (?vin=...). Strips whitespace, uppercases. Queries the database: SELECT recall_id, source_file, MIN(raw_row) AS raw_row FROM recalls WHERE vin = ? GROUP BY recall_id, source_file ORDER BY recall_id, source_file. Returns JSON: {vin, found: bool, message, recall_count, recalls: [...]}.
03
API — /status
Returns total VIN count and number of distinct source files. Useful for ops to verify the database is populated and current.
04
API — /health
Simple {"ok": true} response. Used by the deployment platform for liveness probing.
05
CORS configuration
CORS_ORIGINS env var controls allowed origins. Defaults to * for local dev; set to the production frontend URL in deployment. This lets the static HTML frontend be hosted on a different domain (e.g., Cars24's internal tooling host) while calling the Python API.
06
Deployment
Runs via gunicorn: gunicorn "app:app" --bind 0.0.0.0:5000. Environment variables control VIN_DB_PATH, HOST, PORT, and CORS_ORIGINS — no config files needed for deployment.

Business Impact

Ops team can check any vehicle VIN against the recall database in real time via a browser interface — no technical knowledge required
Decoupled architecture: the HTML frontend can be updated or rehosted without touching the API
SQLite local database means zero external API cost per lookup — all queries run against a local file
CORS configuration makes it safe to host the frontend on Cars24's existing tooling infrastructure without CORS errors
/status endpoint lets the ops team verify data freshness at a glance

Limitations & Future Improvements

Database must be manually updated when new recall data is published — a future version would automate periodic ingestion from the government recall data source.
SQLite is sufficient for low-to-moderate concurrent traffic; a PostgreSQL backend would be needed if the tool is opened to high-volume concurrent access.
The /lookup endpoint returns the full raw recall row — a future version would parse the raw row into structured fields (recall title, severity, issued date, affected models) for a cleaner API response.
No authentication on the API currently — appropriate for internal ops tooling but would need an API key layer before any public-facing use.
