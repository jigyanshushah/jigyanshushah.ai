Problem Statement

Cars24 AU needed a structured, up-to-date map of OEM authorised service centres across Australia — by make, state, suburb, and capability (sales/service/parts). This data is used for marketplace intelligence: understanding the service ecosystem a buyer enters when they purchase a vehicle.

The challenge: OEM dealer locator pages don't expose clean APIs. Most of them render dealer cards via JavaScript after the page loads — with XHR/fetch calls to internal APIs that aren't publicly documented. Simple HTML scraping misses most of the data.

What I Built

A multi-brand async Python scraper using Playwright (headless Chromium) that:

Loads each OEM dealer locator page with a real browser and intercepts all XHR/fetch responses during page load, capturing JSON API payloads. Extracts dealer records from both the rendered HTML and the captured API responses. Normalises all records into a standard schema (17 fields: name, make, state, suburb, address, phone, website, sales/service/parts flags, confidence, etc.). Deduplicates across sources by make + dealer name + address. Exports to a multi-sheet Excel file (main data + make/state summary) and CSV.

Brands: Toyota, Hyundai, Ford, Kia, Mazda, Mitsubishi, Nissan, Volkswagen, Honda, Subaru.

Primary
XHR / JSON API Discovery
A response listener captures all XHR/fetch calls during page load. Responses with Content-Type: application/json or URLs containing "dealer", "retailer", "locator" are parsed and walked recursively for dealer record objects. Captures data that HTML-only scrapers miss entirely.
Fallback
HTML Card Extraction
BeautifulSoup finds dealer cards via CSS selectors ([class*=dealer], [class*=location], article, .card) and extracts name, phone, state from rendered text. Runs in parallel with JSON strategy; records are merged and deduped.

How It Works

01
Config-driven
Brand URLs and scraping mode are defined in config/brands.yaml. Adding a new brand is a one-line YAML entry — no code changes required.
02
Playwright browser launch
For each brand, a headless Chromium browser loads the dealer locator URL. The viewport is set to 1440×1200 to trigger desktop layouts. Common consent dialogs ("Accept all", "Agree") are dismissed automatically.
03
Network interception
A response listener captures all XHR/fetch responses during page load. Responses with Content-Type: application/json or URLs containing "dealer", "retailer", "locator" keywords are captured and parsed. This is the key innovation: many OEM locators don't render dealer data in the initial HTML — they fetch it via undocumented internal APIs.
04
Scroll-triggered loading
After DOM load, the browser scrolls the page 6 times (1200px each) with 1-second waits between scrolls, triggering lazy-loaded dealer map components that only load when in view.
05
Dual extraction
Two parallel extraction strategies run: JSON payloads: extract_dicts() recursively walks each captured API response looking for objects with name + address/suburb + phone/URL fields and dealer terminology. Records normalised into DealerRecord objects. HTML card fallback: extract_from_html() uses BeautifulSoup to find dealer cards via CSS selectors, extracting name, phone, and state from rendered text.
06
Normalisation
normalize_candidate() maps raw field values into the standard schema. State is inferred from explicit state fields, text matching against state names/abbreviations, or postcode-to-state lookup. Service/sales/parts flags are inferred from boolean fields or keyword presence in the record text.
07
Deduplication + export
Records are deduplicated by (make, normalised dealer name, normalised address) key. Output goes to Excel (two sheets: full data + make/state summary via groupby) and CSV.

Tech Stack

Scraping + Processing
Python Playwright — Chromium headless asyncio BeautifulSoup — lxml pandas
Output + Config
openpyxl YAML (config) CSV (stdlib) regex (stdlib)

Playwright is required (not requests/selenium) because OEM locator pages use JavaScript-rendered content and XHR-based data fetching. The async architecture means each brand's browser session runs independently.

Business Impact

Built a structured, deduplicated map of 700+ OEM authorised service centres across Australia across 10 makes
Config-driven brand list means new makes can be added in minutes — no code changes
Make/state summary sheet in Excel gives immediate visibility into service centre density by region — useful for marketplace supply/demand analysis
Dual extraction strategy (HTML + XHR API discovery) captures data that HTML-only scrapers would miss entirely on modern OEM locator pages
Debug output (network URLs, JSON payloads, candidate records per brand) makes it easy to diagnose when a new OEM locator changes its API structure

Limitations & Future Improvements

Some OEM locators require postcode-based search to load dealer results — a future version would iterate through Australian postcodes to ensure full coverage for these brands.
Phone number and website fields have inconsistent availability across brands — a future version could enrich missing contact data via Google Places API or similar.
The scraper captures a point-in-time snapshot; a recurring scheduled run (e.g., monthly) would keep the dataset current as dealers open, close, or change locations.
Sales/parts/service flags rely on keyword inference when OEMs don't expose them as explicit boolean fields — confidence is "Medium" in those cases; a manual validation pass could promote them.
